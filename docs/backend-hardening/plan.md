# Backend review corrections: implementation plan

This is the handoff plan for correcting the backend review of PandaBlog. **Do not edit this file to record progress.** Use [`progress.md`](./progress.md). The baseline finding register and evidence are in [`findings.md`](./findings.md).

**Status: planned, not implemented.** This package does not supersede the completed logging redesign; it extends its safety guarantees where the review found gaps. See [logging progress](../logging/progress.md) for historical decisions and still-open production gates.

## Runtime startup/configuration follow-up (2026-10-07)

A subsequent investigation found a Nitro startup integration gap: async plugins are not awaited, so writer acquisition can fail before protection is installed while DB initialization proceeds. Follow [runtime startup/configuration plan](../runtime-startup-config/plan.md) and [progress](../runtime-startup-config/progress.md) for the corrective tasks, canonical environment-name migration, approved removal of ordinary runtime ROOT fallback in development and production, and approved footer attribution rename to `NUXT_PUBLIC_FOOTER_SHOW_POWERED_BY`. This follow-up does not replace the existing recovery/restore invariants or authorize deployment; startup coordination must be resolved before claiming safe writer enforcement through the actual runtime.

## How to use this plan

Ask the implementing agent:

> Read `docs/backend-hardening/progress.md`, then implement **REV-1.4** from `docs/backend-hardening/plan.md`. Follow the referenced specs, add regression tests, and update progress before handing off. Do not operate on configured application or production data.

For a longer delegation:

> Implement the next unblocked task in `docs/backend-hardening/plan.md`. Continue in dependency order, recording each completed task and verification result in `progress.md`. Stop only for a genuine blocker or a decision that would change security, data preservation, API compatibility, or deployment architecture.

The agent must:

1. Read progress, this task, [spec 00](./specs/00-architecture.md), and every spec referenced by the task.
2. Recheck the current implementation; file line numbers in the review are baseline navigation hints, not immutable locations.
3. Confirm prerequisites are `done`. If not, implement an eligible prerequisite or record a blocker; do not silently bypass it.
4. Add the smallest useful failing regression before changing behavior. Isolate fixtures from `.env`, existing storage and production.
5. Stay in task scope. If evidence disproves a finding or a design cannot be implemented safely, document the evidence and deviation before changing the contract.
6. Run the definition-of-done checks and the task-specific acceptance tests.
7. Update the progress status table, findings disposition, decisions, session log, and remaining release gates. Do not claim production verification from mocked or synthetic tests.

## Definition of done

For every code task:

- `npm run lint`, `npm run typecheck`, `npm run test:unit`, and `git diff --check` pass. Record pre-existing unrelated failures explicitly rather than fixing them opportunistically.
- Relevant security/correctness regressions are automated; tests must be committed, not ignored. Inspect `.gitignore` when adding test files.
- Changed SurrealQL is exercised on **isolated stable SurrealDB 3.2.x** (user-approved amendment; explicit fixture/CI pin 3.2.4; record exact build) with the installed SDK. Unit mocks alone do not validate transactions, index ordering, permissions, datetime behavior, or import semantics.
- Supported production **Node 22** is tested; local Node 24 results are supplementary.
- Existing API/UI contracts are retained unless the task explicitly specifies an additive or coordinated change. New user-facing text is translated in both `i18n/locales/en.json` and `i18n/locales/zh-CN.json`.
- Schema changes include idempotent migration, interrupted-run behavior, legacy-data behavior, and an operator recovery note. No destructive reset is hidden in schema initialization.
- Optional modules still build and run when disabled. Temporary probe endpoints, fixture credentials and diagnostic instrumentation are not shipped.
- Local acceptance and external release acceptance are recorded separately. `done` means the task's local deliverables are complete; missing required local DB/runtime evidence means `blocked`, not a passing claim. Production-only gates can remain pending after local completion.

Docs-only tasks require link/task/dependency consistency and `git diff --check`, not a new application test run.

## Phases and deployment boundaries

| Phase | Goal | Deployment boundary |
|---|---|---|
| 0 | Preserve evidence and establish reproducible isolated tests | No runtime change |
| 1 | Close security gaps and remove destructive startup reset | Auth epoch schema + readers + all writers deploy together; ZIP privacy and Archiver fix deploy together |
| 2 | Make DB lifecycle and destructive jobs safe | Restore fence, persistent journal, streams and recovery must deploy together |
| 3 | Bound media resources and make filesystem changes race-safe | Publication/deletion state + reference writers + cleanup readers deploy together |
| 4 | Bound analytics, logs, graph/search and cache work | Analytics summary publication/checkpoint/readers deploy together; preserve logging migration receipts |
| 5 | Prove combined behavior and prepare release | Production remains blocked until operator gates pass |

Tasks in independent lanes may be implemented in parallel, but they must not overwrite shared files or each other's progress. Assign one integrating agent for `schema.surql`, `db.ts`, `settings.ts`, and shared maintenance/admission interfaces.

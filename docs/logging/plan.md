# Logging redesign: implementation plan

This is the plan for redesigning PandaBlog logging. **Do not edit this file to record progress.** Use [`progress.md`](./progress.md) for that.

## How to use this plan

To run a task, ask the agent:

> **"Implement LOG-1.1"** (or several: "Implement LOG-1.1 and LOG-1.2")

The agent must:

1. Read [`progress.md`](./progress.md) to check current state, blockers, and notes from earlier sessions.
2. Read this file's entry for the task, then **every spec it references** (and [`specs/00-architecture.md`](./specs/00-architecture.md), which always applies).
3. Check that all tasks in **Depends on** are `done` in progress.md. If one is not, stop and report it.
4. Implement the task. Stay inside its scope. If a spec is wrong or can't be done as written, make the smallest reasonable deviation and write it down under *Decisions / deviations* in progress.md.
5. Run the **Definition of done** checks (below).
6. Update progress.md: the status table, a session-log entry (what changed, which files, test results, follow-ups), and any manual verification still left for the operator.

Status values in progress.md: `todo` · `in-progress` · `blocked` · `done` · `skipped` (with a reason).

### Definition of done (every code task)

- `npm run lint`, `npm run typecheck`, `npm run test:unit` all pass. If a failure existed before the change, note it in progress.md instead of fixing unrelated code.
- New pure logic has unit tests in `tests/unit/`.
- New user-facing strings exist in **both** `i18n/locales/en.json` and `i18n/locales/zh-CN.json`.
- New settings follow the checklist in spec 00 §5.
- The spec's acceptance criteria are met, or listed as "manual verification pending" in progress.md.

## Phase overview

| Phase | Goal | Outcome |
|---|---|---|
| **0: Baseline** | Measure before changing anything | Numbers to compare against |
| **1: Stop the bleeding** | Errors visible in `docker logs`, retention enforced, less noise, smaller backups | DB stops growing, production errors are visible |
| **2: Access logs out of the DB** | High-volume stream moves to rotating files | `access_logs` table removed |
| **3: Error groups** | Error inbox grouped by fingerprint | Usable error triage |
| **4: Wrap-up** | Cleanup and operator docs | Done |

Phases are ordered, but Phase 3 depends only on Phase 1, so it can be done before Phase 2 if errors matter more.
